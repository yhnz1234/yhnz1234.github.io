Git与Github

学完整理，给同样是新手的人看。看完这个，基本的 Git 概念就不慌了，具体命令直接交给 AI 敲就行。

写在前面：为什么要学 Git

现在 AI 编程工具一堆，核心操作全围着 Git 转。好消息是 AI 时代根本不用死记硬背命令，把概念搞懂，剩下的事情用大白话指挥 AI 就行。

1. Git 到底是个啥

一句话：版本控制。就是给你文件夹装个”后悔药”。

写论文的时候谁没干过这种事——“论文第一版””第二版””第三版””定稿版””最终版打死不改”，每次小心翼翼地保存，就怕哪天要找回某个历史段落。Git 就是把这套纯人工操作自动化了。

  • 被 Git 管的文件夹叫仓库，里面会多出个 .git 子文件夹，所有版本信息都藏在这。
  • 基本单位是 commit（提交），每提交一次就是存一份快照，提交越攒越多，串成一条历史链路，随时能翻旧账。

想说：把 .git 文件夹删了，这个文件夹就”退管”了，不再是 Git 仓库。

2. GitHub 是干嘛的

Git 管本地，GitHub 管云端，名字拆开就是 “Git” + “Hub”（集散地）。全世界的开发者把仓库往上一放，就变成代码托管 + 协作平台。

  • 仓库分公开（所有人都能看到代码、学习）和私有（只有自己能看）。
  • Linux、Python 官方解释器这些巨无霸都开源放在上面，开源真的是计算机世界的基石。
  • 除了 GitHub 还有 GitLab、Gitee，概念一样，会一个全都会。

3. 本地四个核心概念

  • init：初始化，让文件夹变成 Git 仓库。第一步，别漏了。
  • .gitignore：声明哪些文件不让 Git 管。这个超级实用——密钥 .env、node_modules/ 这种上千个文件的依赖目录，都不该传上去。
  • commit：提交改动。每次提交有一个唯一 id（commit id / 哈希），跟 AI 说话时直接报这个 id 最精确。
  • branch（分支）：仓库的平行世界。每个分支的改动互不影响，开发完 merge 合并回主干。分支本质是指针，不是拷贝代码，所以创建分支快得很。

我一开始以为分支就是复制一份文件夹，后来才知道只是挪了个指针，轻量得很。

4. 三种”后悔药”

这是我最喜欢的部分，Git 的撤销分三种，场景完全不同：

  • discard：文件改了但还没 commit，想反悔？直接放弃这次改动。
  • reset：强制回退到某个历史状态。只在单人分支、且改动没推到远端时用。一旦推到远端再 reset，就得强制推送覆盖，容易把代码搞丢，多人分支上严禁。
  • revert：生成一个反向提交来抵消，历史干净又安全，多人协作回退优先用它。

记住一句口诀：单人 reset、多人 revert，改一半没提交就 discard。

5. 四个分区，理解文件怎么流动

这是理解 Git 的关键，其实就是文件在这几个区域之间搬运：

工作区（你磁盘上的文件夹）→ 暂存区 → 本地仓库 → 远端仓库（GitHub）

  • add：工作区改动放进暂存区（commit 前的检查点）
  • commit：暂存区的东西固化进本地仓库
  • push：本地仓库推到远端（别人才能看到）
  • pull = fetch + merge：把远端最新改动拉回本地

VS Code 里点 commit 按钮其实是”add + commit”一步到位，把暂存区藏起来了。想分开用也可以，文件右侧的加号就是 stage。

6. 本地 ↔ 远端怎么绑

就两条路：

  • clone：远端仓库克隆到本地，同时建好本地仓库 + 工作目录。我第一次用就是干这个，桌面多了个文件夹，很直观。
  • 先 init 再 push：本地先建仓库，提交后再推到远端。

提醒：想 push 进别人仓库，你得是管理员或协作者才行，别瞎试。给开源项目贡献代码有专门流程，见第 8 节。

7. GitHub 页面常用功能

  • star：相当于点赞收藏，反映项目热度。
  • fork：把项目复刻一份到自己名下，可以随便改、随便玩，是开源贡献的第一步。
  • issues：和作者/社区讨论的地方，报 bug、提需求都在这。看开源项目前先翻翻 issues，很多坑别人都踩过、有答案了。
  • releases：正式发布的版本，一般有打包好的安装包。
  • README：仓库门面，作者都会把”这项目干嘛的、怎么用”写在这。

好用的快捷键（记不住没事，按 ? 能弹出速查表）：

  • / 全局搜索、t 搜文件、l 跳转行号
  • . 直接在浏览器里打开网页版 VS Code 看代码

8. 开源协作完整流程（重点！）

想给开源项目贡献代码，走这条路：

fork 母项目 → 克隆自己名下的副本 → 先建分支（别直接改主干！）→ 改代码 → commit → push → 创建 Pull Request（PR） → 管理员 code review → 合并进主干

三个关键点：

  1. 一定先建分支。改完同步上游代码时才不会和主干打架。
  2. 提 PR 前先同步母项目最新代码。两个分支改了同一行就会冲突，先在本地解决掉再提。
  3. 管理员在 PR 里能看到你改的代码，可以提意见，没问题就 merge，你的名字会出现在贡献者列表里，成就感拉满。

如果是公司内部/被加为 collaborator，可以省略 fork，直接建分支 push 就行。

9. 几个进阶概念

  • HEAD：就是”当前在哪”，指着仓库现在处于哪次 commit。说人话：Git 的”你在这儿”。
  • worktree：把某个分支复制到新的文件夹，两个文件夹并行开发互不干扰，写累了还能在另一个地方开窗口。
  • merge conflict（合并冲突）：两边改了同一行，Git 也不知道留哪个，只能人工（或让 AI）决定。刚学别慌，遇到一次就会了。
  • cherry-pick：只想挑某几次提交搬走，不需要整条分支。字面意思”挑樱桃”，很形象。
  • stash：代码写一半要紧急切分支，先把半成品存起来，干完活回来再 pop 拿出来继续写。比临时 commit 优雅多了。
  • rebase（变基）：把自己分支的”地基”挪到 main 上，历史会变得超干净（没有一堆 merge 记录）。但根基变了必须强制推送，只能单人分支用，多人分支千万别碰。

最后

别被命令吓到。核心就是理解上面这几个概念：commit 是存档、分支是平行世界、push/pull 是搬运、revert 是安全撤销。剩下具体命令，用大白话跟 AI 说就行，它帮你敲。
